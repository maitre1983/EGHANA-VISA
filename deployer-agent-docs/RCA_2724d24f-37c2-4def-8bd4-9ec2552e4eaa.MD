## Goal answer — initiate vs status IP restriction
The initiate-vs-status IP question **cannot be answered from live traffic yet**, because production has made **no** `POST /items/initiate` and **no** status call since the flag flip.

What IS proven:
- **Network reachability to `payproxyapi.hubtel.com` from the prod egress IP is fine** — the diagnostic GETs returned a real HTTP 404, not a timeout / connection-refused. DNS+TCP+TLS to that host succeed. This rules out a blanket network/firewall IP block on the payproxyapi host.
- It does NOT rule out an **application-layer** IP allowlist that Hubtel may enforce only on the authenticated `POST /items/initiate` (that would come back as HTTP 401/403 from Hubtel, surfacing as a `server - ERROR - Hubtel checkout failed:` line) — untested, since no POST was made.
- Nothing is known about `api-txnstatus.hubtel.com` IP restriction — zero calls.

Also note: the current build (first to have both the working `/payments/initiate` route AND `sandbox=false`) only went live at 18:47, so there has effectively been no window with real live checkout traffic.

Drive ONE real live checkout against production (create an application, `POST /api/payments/initiate`) to generate an actual `/items/initiate` call, then re-read logs for `Hubtel checkout failed:` — its message carries Hubtel's HTTP status / responseCode / message and will directly show whether initiate is IP-rejected.
