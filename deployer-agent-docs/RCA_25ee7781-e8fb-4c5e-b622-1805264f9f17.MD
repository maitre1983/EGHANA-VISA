Because the production backend pods run on the **same cluster (target-2)**, they egress through the **same Cloud NAT**, so this is the IP (or one of the IPs) Hubtel would see.

## 2. Is the egress IP static / stable?

**Cannot be fully guaranteed from available tooling — this is a Platform/infra fact, not an app fact.** Caveats the user must understand before whitelisting a single IP:

- The egress IP is set by the **cluster Cloud NAT gateway**, not by the app. It is NOT affected by the app's code, pod restarts within the cluster, or redeploys *as long as the app stays on cluster target-2*.
- A Cloud NAT gateway commonly has a **pool of multiple IP addresses** and may source different connections from different IPs in that pool. A single observation (130.211.210.175) does not prove it is the ONLY egress IP.
- Whether these NAT IPs are **reserved/static** vs. auto-allocated (which can change) is a GCP Cloud NAT configuration detail I have no tool to inspect.
- If the deployment were ever migrated to a different target cluster, the egress IP would change.

**Recommendation:** Whitelist the full set of NAT egress IPs / CIDR for cluster target-2 confirmed by Emergent infra, rather than only the single observed 130.211.210.175. Open an Emergent support ticket (quote deployment `2c861289-b5f5-4b46-a752-993f9f7157b3` / job `cdaa271d-06cc-46a9-a935-2481b2ae1af3`) to get the authoritative, stable egress IP list/range and confirmation of its stability guarantee.

## 3. Hubtel errors in logs

Backend logs for the active run were scanned (filter: `hubtel|403|txnstatus|status check failed`).

**Tool limitation:** log retention lookup is capped at 1440 min = **24h**, so I covered the **last 24h, not the full 48h requested**.

Findings in that 24h window:
- **No** `"Hubtel status check failed"` messages.
- **No** HTTP 403 from `api-txnstatus.hubtel.com`. In fact no traffic to `api-txnstatus.hubtel.com` appeared at all in-window.
- Observed only two benign entries: `GET https://payproxyapi.hubtel.com "HTTP/1.1 404 Not Found"` — these are GETs against the Hubtel base URL returning 404 (expected; not a 403/auth/whitelist rejection).

So there is **no evidence of IP-whitelisting rejection (403) in the last 24h**. To confirm the full 48h, the user should check the live app / their own Hubtel dashboard, as the deployer log tool cannot reach back 48h.
